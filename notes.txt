ASCII-art is a great idea, let's push it to the full extent to allow schematic design of arbitrary complexity!

Maybe lets make the hole definition a bit more straightforward. Essentially every component in the block is a "hole" until it's bound, including Cn and Rn components. In your opamp U1 example, U1 is a hole which is bound to an atom. We probably want to get away from term "hole" and instead name them "unbound" and "bound" component

Spaces designate empty space, but the proposed sparse dot grid is also helpful for visual aiming


### sub-component names locality

The component names having the single block scope. I.e. U1 in different blocks are different U1

### adjacency

The component rectangles are not allowed to touch directly, even if there is no wires between them required or the wiring is direct and obvious

There has to be a gap of at least 1 column/row

## buses


Also, we cannot keep the `An element in a single cell has at most one port per side` constraint because it'll be a very serious handicap.

Instead, we introduce a concept of a bus - a numbered and optionally named set of wires on each side of a rectangular component

The bus is strictly ordered and parallel (meaning non-intersecting) bundle of wires along its length

*(I'm debating whether we should translate our ASCII bus into KiCad schematics bus.

### taps

only 1-wire taps permitted, but there has to be a way to name the wire, something like this


### buses and the block sides (external interface)

The wires and buses reaching block sides are considered external interfaces. The order matters

```
.<a>===
.<b>---
.
.<c>===
```
the above example means the right pins of the block is [a.pins, b, c.pins]

*(Naming buses will help if we translate them to KiCad buses)*


The pins on each side of the block have to be explicitly depicted with bus or wire symbols. Placing a component on the edge of the block is not sufficient to export its pins



### buses and components

A component may have 1 or more buses and/or wires connected to each side

The order matters, for vertical sides left and right numbered from the top. For horizontal sides top and bottom numbered from the left to right.

```
U1U1
U1U1════╗
U1U1    ║
        ╚═════U3
              U3═══
  ╔═══════════U3
U2U2
U2U2
U2U2
```

In the above example, the left pins of U3 connected to [U1.right.pins, U2.top.pins]



### many buses on 1 side

Using many buses on 1 side of the component is allowed only if there is a way to bind each bus pins, i.e. there should be a root component to begin inferring bus width.
When (n-1) component buses are bound the last one may be inferred.

For example

```
  U1U1
  U1U1════╗
  U1U1    ║
          ╚═════U3

  U2U2
```

so pins on <ext> bus could be inferred since we know that U3 left pins list is [U1.right.pins, ext.pins, U2.top.pins] and U1.right and U2.top is uniquely bound


### component rotation/mirroring

The rotation and mirroring matters and renumbers the pins on the connected bus to preserve planarity - **not sure how to escape this complication to avoid cross-wiring adapters or using KiCad buses**

- **If the schematic block shows 1-wire on U1, binding 2-wires will likewise cause an error**

## LAYOUT

The ASCII should not only allow creating valid netlists but must also directly translate into readable KiCad schematic - this is where planarity matters

The KiCad atoms could be only rotated or mirrored, but cannot be stretched. At the same time, the binding flexibility can stretch other rectangle components on the block.

For example U1 and U2 components below may have the same ASCII size, but actual binding can inflate U2 considerably compared to U1 and the U1.right = U2.top bus has to be adjusted accordingly on kicad schematic.

```
      ╔════╗
U1U1  ║   U2U2
U1U1══╝   U2U2
U1U1      U2U2
```

Let's use Java grid-bag like layout to address this, with the stretching to be done only to wires and buses.


### Stretching

The fundamental transformation required for Grid-bag layout implementation is stretching (or shrinking)


Stretching triviality: horizontal wires trivially stretched when block width has to change or move horizontally. Likewise vertical wires height changes when moving/stretching vertically.

Therefore we only need to consider scenario when horizontal pins have to be shifted/stretched to adjust Y axis (scale/shift). Vertical pins have to be sifted/stretched when X axis (scales/shifts)

Since both X/Y axis transformations computed/applied independently we just need to come up with single set of rules for both


**Triviality**

the opamp with 2 horiz pins to the left and 1 horiz to the right

```
.  |          |  .
.  |          3--.
.  |          |  .
.--2          |  .
.  |          |  .
.  +----------+  .
..................
```

shift/stretch in X axis will be simple, like below, i.e. internal atom - the actual kicad component size never stretches

The dots here represent the outer size of the block while the inner atom size stays the same

**Adjustments**

The outer (dotted) block size of the atom is the size with wire adapters

The wire adapter would have to provide the shift/scale capability in "ladder" fashion to prevent intersections. For example for vert pins transformed along X
```
.      | | | |       .
.+-----1-2-3-4------+.
.|                  |.
<--------sz_x-------->
```

```
.    |                  |            | |.
.    └-┐                |            | |.
.      | ┌--------------┘            | |.
.      | | ┌-------------------------┘ |.
.      | | | ┌-------------------------┘.
.      | | | |                          .
.+-----1-2-3-4------+                   .
.|                  |                   .
<--------------sz_X--------------------->
```


I.e. we can shift every pin individually still preserving the order and avoiding intersection

An example why we want to do that is the 4 pin block attached above might have an internal structure with different block width and their pins spacing that mimics underlying atoms that have their own pin coordinates

Since it's a ladder, adapting wires horizontally adds height to the outer size, so let's not forget about that, i.e. sz_y increases
